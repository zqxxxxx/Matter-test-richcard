# Richcard LLM Business Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the current richcard validation loop from seeded/static acceptance data into a real end-to-end LLM business loop for group summaries, Matter extraction/status updates, and card feedback.

**Architecture:** Keep cards as the presentation layer in `octo-web`; put LLM calls in `octo-matter` and `octo-smart-summary`; use backend events to send business-card messages back to the source group through Octo IM. Every closed loop must prove: user action -> backend/API -> LLM or deterministic fallback -> database result -> richcard message in original group -> click jumps to the owning module -> feedback updates backend state.

**Tech Stack:** React/TypeScript (`octo-web`), Go (`octo-matter`, `octo-server`), Docker Compose deployment (`octo-deployment/docker`, `octo-deployment/richcard-demo`), MySQL, summary-api/summary-worker, OpenAI-compatible LLM gateway.

---

## Scope

This plan covers productionizing the richcard LLM loops. It does not redesign the existing card visuals unless a new backend field is required for clarity.

## File Structure

- `octo-deployment/docker/.env` or server deployment env: real `LLM_API_URL`, `LLM_API_KEY`, `LLM_MODEL`, `COMPOSE_PROFILES=summary`.
- `octo-deployment/docker/docker-compose.yaml`: already carries Matter and Summary LLM env; verify and adjust only if env names mismatch runtime.
- `octo-deployment/richcard-demo/scripts/`: replace seed-only scripts with scripts that can create real tasks and validate generated records.
- `octo-matter/internal/service/extract_svc.go`: Matter extraction from chat messages.
- `octo-matter/internal/service/timeline_svc.go`: progress extraction from timeline/comment content.
- `octo-matter/internal/service/v2_svc.go`: Matter v2 agent/project/card behavior.
- `octo-matter/internal/notification/`: confirm Matter status events can notify Octo IM.
- `octo-web/packages/dmworktodo/src/utils/businessCard.ts`: consume backend/Matter fields, remove fake agent labels.
- `octo-web/packages/dmworkbase/src/Messages/BusinessCard/BusinessCardView.tsx`: render returned fields without static demo assumptions.
- `octo-web/packages/dmworksummary/src/api/summaryApi.ts`: existing summary create/respond/regenerate API client.
- `octo-web/e2e/richcard-full-acceptance.spec.ts`: extend acceptance to verify LLM-generated content and automatic card return.

## Key Product Acceptance Criteria

- No P0 path depends on prewritten `summary_result` content.
- No P0 path depends on `send-richcard-messages.sh` injecting final cards.
- Matter cards are created from real Matter records and sent back automatically after state changes.
- Summary cards are created from real summary tasks and regenerated after feedback.
- Every card has a clear module jump and return-to-chat path.
- LLM failure produces understandable degraded UI, not a dead end.
