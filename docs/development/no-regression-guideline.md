# 防串改开发规范

这份规范用于降低“改 A 坏 B”“局部修复影响共享链路”“上线后才发现缓存或部署不一致”的概率。适用于前端、后端、全栈功能、原型转生产代码、AI 辅助开发。

## 核心原则

任何改动都必须先回答三个问题：

1. 这次到底改什么？
2. 哪些共享链路可能被牵连？
3. 用什么证据证明没有改坏旁边功能？

如果回答不清楚，先不要动代码。

## 一、先定边界

开始实现前必须写清楚：

- 本次目标：一句话说明要解决的问题。
- 允许改动范围：可以改哪些模块、页面、接口、组件、数据表、配置。
- 禁止改动范围：明确不碰哪些功能和链路。
- 潜在影响对象：列出共享依赖、相邻业务和历史兼容场景。

示例：

```text
本次目标：修复群总结卡片折叠态信息不足。
允许改动：群总结卡片 UI、群总结卡片 adapter、相关测试。
禁止改动：matter 卡片业务逻辑、消息发送接口、登录态、后端数据结构。
潜在影响：群聊消息渲染、业务卡片聚合、右侧栏预览、旧群总结卡片兼容。
```

## 二、共享层自动升风险

只要碰到以下内容，就不能按小改动处理：

- 消息渲染链路
- 通用卡片组件
- 状态聚合函数
- 路由和跳转
- 登录态、权限、空间隔离
- 数据同步、通知、回调
- 缓存策略、Nginx、构建产物
- 公共 utils、adapter、service、handler
- 数据库迁移和公共模型
- 多业务共用的 UI 壳层

共享层改动必须做交叉回归，不能只测当前需求。

## 三、先补保护测试

开发顺序固定为：

1. 复现问题或确认现状。
2. 补最小保护测试。
3. 确认测试能锁住关键行为。
4. 修改实现。
5. 跑窄范围测试。
6. 跑相关链路回归。
7. 再部署或交付。

如果是 UI 调整，至少要有核心流程冒烟测试：

- 页面能打开。
- 核心按钮能点击。
- 状态能保存或同步。
- 刷新后仍可用。
- 相邻业务没有被破坏。

## 四、业务隔离，公共层参数化

多个业务共用同一套组件或链路时，遵守：

- 公共层只提供机制，不写死某个业务的规则。
- 业务差异放在 adapter、config、renderer 或 strategy 中。
- 不在公共函数里硬编码单一业务类型。
- 新增业务类型时，必须验证旧业务类型不变。

推荐结构：

```text
shared renderer / aggregator
  -> matter adapter
  -> summary adapter
  -> other business adapter
```

## 五、提交前必须输出影响面清单

每次实现完成后，交付说明必须包含：

```text
本次改动：
- 改了什么

直接影响：
- 哪些功能一定变化

潜在影响：
- 哪些共享链路可能受影响

明确未改：
- 哪些功能没有动

验证方式：
- 跑了哪些测试
- 手工验了哪些流程
- 线上版本或构建产物是什么

残留风险：
- 哪些场景没有覆盖
```

## 六、测试数据必须可识别

所有测试数据使用固定前缀：

- `[SMOKE]`：冒烟测试。
- `[QA]`：人工验收。
- `[REGRESSION]`：回归测试。
- `[DO-NOT-DELETE]`：长期保留测试样本。

禁止生成看起来像真实业务的数据。清理测试数据时，只允许清理带测试前缀的数据，不能模糊删除。

## 七、部署检查不能省

部署前必须确认：

- 前端包是否重新构建。
- 后端服务是否重新构建。
- 共享包是否被包含。
- 静态资源是否刷新。
- 浏览器缓存是否可能命中旧包。
- 当前线上实际加载的 bundle 或镜像是否为新版本。

上线后必须验证线上实际行为，不能只看本地测试。

## 八、按用户链路回归

不要只问“我改的文件测了吗”，要问“用户路径还通吗”。

典型业务卡片回归清单：

```text
创建
同步到群聊
群聊展示
折叠态
展开态
右侧栏或详情
状态更新
刷新页面
重新进入群聊
旧数据兼容
相邻卡片类型不受影响
```

## 九、发现串改时先停手

一旦出现“修一个坏一个”，流程必须切换成排障模式：

1. 暂停新增功能。
2. 找共享链路。
3. 找最近改动。
4. 找缺失测试。
5. 补保护测试。
6. 做最小修复。
7. 跑交叉回归。

不要靠继续叠补丁解决串改。

## 十、交付必须有证据

不要只说“已修复”。必须提供：

- 改动文件。
- 测试命令。
- 测试结果。
- 部署版本。
- 线上校验结果。
- 未覆盖风险。
- 测试数据是否保留。
